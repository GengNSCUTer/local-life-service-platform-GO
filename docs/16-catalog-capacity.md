# 店铺目录与社交容量基线

## 数据与场景

本轮在 3090 的本机隔离环境中执行 `catalog`。测试进程绑定 `127.0.0.1`，工作目录位于仓库的 `runtime/stage7-catalog.*`。MySQL、Redis 与 Kafka 使用本轮专用的端口和数据目录。脚本退出时先停止并回收子进程，再删除试验数据库、Redis AOF、Kafka 数据和 Go 可执行文件，保留日志与指标。

| 数据 | 规模与分布 |
| --- | --- |
| MySQL 用户 | 100,000 个合成手机号和昵称 |
| 店铺 | 10,000 家、10 个分类。四个地理中心，半数店铺在同一热点中心 |
| 博客 | 1,000,000 条，每条关联已有作者和店铺 |
| 关注 | 1,000,000 条，每个用户关注 10 人，交叉关联经 SQL 核验 |
| Redis 会话 | 10,000 个，对应已落库用户，初始 TTL 30 分钟 |

造数以每批 2,000 行的 SQL 导入，再通过 Redis pipeline 建立带 TTL 的会话。冒烟通过真实接口领取和核销验证码、查询资料与店铺、检验四个中心 5 公里内的 GEO 距离排序和热点深页、检验关注动态游标连续两页。冒烟通过 `POST /blog` 额外发布一篇博客，跟踪其通知由 Worker 经 Kafka 到达关注者的 Redis。

压测用同一组 12 条读路径，每个客户端轮询。变量为 API 数量（1 或 2）、分布（均匀或热点）与 Redis 店铺缓存状态（冷启动或预热）。每组 16 个闭环客户端持续请求 60 秒，使用 HTTP Keep-Alive，双 API 组在两端口间交替发请求。均匀组覆盖全部店铺、全部 10,000 个令牌及全部分类。热点组将约 90% 的可变访问集中到前 20 家店铺、前 20 位登录用户及热点分类和坐标。冷启动组从空的详情与 GEO 缓存启动，运行中允许正常回填。预热组提前经 HTTP 查遍全部 10,000 家店铺及 10 个分类的 GEO。MySQL 缓冲池在各组间复用。

## 复现

```bash
export MYSQL_BIN_DIR=/path/to/mysql/bin
export REDIS_BIN_DIR=/path/to/redis/bin
export KAFKA_BIN_DIR=/path/to/kafka/bin
STAGE7_BASE_PORT=31120 CATALOG_CLIENTS=16 CATALOG_SECONDS=60 scripts/stage7-local.sh catalog
```

`catalog-results.jsonl` 包含各组和各端点的请求数、错误样例、P50/P95/P99。`catalog-explain.txt` 包含单独执行的 MySQL `EXPLAIN ANALYZE`，用于查看执行器实际扫描行数。HTTP 延迟还包含 Gin、Redis、连接池、编码与客户端。每组前后留有 Redis `INFO`、MySQL 全局状态及两个 API 的 Prometheus 快照。缓存命中统计使用 Redis `keyspace_hits` 和 `keyspace_misses` 差值，包含鉴权、GEO 等访问。

## 3090 实测结果

测试于 2026 年 11 月 20 日运行，使用 Go 1.27.1、MySQL 8.0.33、Redis 7.2.11 和 Kafka 4.1.2 单 Broker。八组共发出 57,006 个请求，成功 56,945 个。全部 61 个失败均来自热门博客第 1,000 页（HTTP 503，应用日志记录查询超时）。其余 11 条读路径没有失败，冒烟校验全部通过。脚本仍保留所有结果，并以退出码 `1` 表示检测到请求错误。延迟百分位基于成功请求。

| 1 | 热点 | 预热 | 7,904 | 4 | 128.8 | 2.54 | 1350.16 | 1524.41 | 70.16% |
| 2 | 均匀 | 冷 | 6,061 | 8 | 99.6 | 7.46 | 1366.30 | 1646.27 | 57.94% |

- 单 API 均匀流量下，预热后详情 P99 从 223.42 ms 降到 1.31 ms，GEO 首页从 433.94 ms 降到 3.68 ms。双 API 热点流量下，GEO 第 90 页 P99 从 1,992.33 ms 降到 11.04 ms。冷启动时同时存在重建、回源和混合负载，单凭这些差值无法量化各项开销。
- 热门博客第 1,000 页的成功请求 P99 在 1.73–2.36 秒之间。双 API 与单 API 共用同一套 Redis、MySQL 和 Kafka，此次双 API 各组约 100–118 请求/秒，单 API 各组约 118–129 请求/秒。下一次扩容对照需要重复采样并单独测数据库。当前数字适用于这组固定的 16 客户端混合读流量。
- 每组 MySQL `Innodb_rows_read` 增量约 5.26–6.85 亿，含全部接口和后台任务。结合执行计划与 HTTP 超时可以定位热门博客深页。Redis 命中率也是实例级口径。双 API 均匀预热组的 Redis 总键数比另外三组预热少 26 个，预热逐项访问了 10,000 家店铺，缓存回填可失败，因此预热组表示测前执行预热流程。
- 已核对本轮监听端口全部释放，MySQL 正常关闭，临时中间件数据目录已清理。报告数据来自本轮保留的 `catalog-results.jsonl` 和 `catalog-explain.txt`。

## MySQL 执行计划

以下为与接口条件、排序和连接方式一致的代表性 SQL，社交查询只投影报告所需字段。服务器单独执行一条查询的时间与 HTTP 压测延迟分别统计。

| 查询 | SQL 最后一行耗时 | 执行器访问的数据 |
| --- | ---: | --- |
| 店铺名称，首页 | 0.096 ms | 扫描 10 行，返回 10 行 |
| 店铺名称，第 990 页 | 17.0 ms | 扫描 9,900 行，返回 10 行 |
| 店铺名称，低命中关键词 | 12.6 ms | 扫描 10,000 行，返回 1 行 |
| 店铺按分类，第 196 页 | 2.12 ms | 分类索引读取 980 行，跳过 975 行 |
| 热门博客，首页 | 0.213 ms | 倒序扫描 `idx_blog_hot` 的 10 条索引记录，再关联作者和点赞 |
| 热门博客，第 1,000 页 | 1,119 ms | 优化器选择全表扫描约 100 万行并做排序，关联后的前 10,000 行中跳过 9,990 行 |
| 关注动态，首页 | 1.12 ms | 10 个关注对象、101 篇候选博客 |
| 关注动态，`id < 900000` | 0.656 ms | 同样 10 个关注对象，90 篇候选博客 |

## 优化优先级

1. **先做热门博客游标。** 给 `GET /blog/hot` 增加可选的 `(liked, id)` 游标，沿现有 `idx_blog_hot` 从上一页末尾向后读。先取目标页 ID，再查作者和点赞。点赞会实时改变排序，若产品要求跨页冻结排名，可用带版本的短周期榜单。复测时重点看深页扫描量和混合流量的 P99。
2. **优化店铺列表和搜索。** 分类列表可以用 `id > afterId` 走索引。名称查询也能用游标减掉深翻页成本，但 `%关键词%` 的低命中搜索仍会扫描大量候选。保留子串语义，先用真实中文词样对比 MySQL 全文检索或专用搜索索引，以召回率和 P99 决定方案。
3. **压低 GEO 和详情缓存重建成本。** 目前每次 GEO 查询先访问 MySQL 读分类版本，冷缓存时可能有多个 API 同时重建。可以在店铺写入后预热 GEO 版本并限制并发重建。详情缓存已有进程内合并，只有双实例热点冷启动实测出现重复回源压力时，再评估跨实例合并。
4. **补高扇出社交数据。** 当前样本中每人关注 10 个作者，每位作者约 10 篇。下一轮加入拥有十万粉丝的作者和高频发帖，观察 Feed 候选行数和通知从发帖到可读的端到端延迟。必要时给通知任务做分批并行，给高活跃用户页面做缓存。
5. **继续按秒杀写路径验收高可用。** 读压测与秒杀落单是两条容量线。活动内库存热点行、Redis 热键、Kafka 分区消费以及多主机场景应继续用订单确认速率、积压和恢复时间验收。见[秒杀优化路线](05-seckill-optimization-roadmap.md)和[阶段 8 容量与发布](14-capacity-and-release.md)。
