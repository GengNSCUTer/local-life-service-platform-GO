# 爆帖、楼中楼与社交通知容量

爆帖同时产生详情读取、点赞和评论。旧写路径需要为每次互动独占 `tb_blog` 的一行，旧详情直接查 MySQL。新版可以按用户 ID 把互动计数分散到 16 行，同时用短缓存承接公共详情。大 V 通知用读时拉取，普通作者的通知仍走 Kafka 和 Redis。

## 回复与计数

`POST /blog/:id/comments` 的 `parentId` 可以指向同一篇帖子的任意未删除评论。顶层评论下按 ID 平铺。读取时，`parentId` 是用于分页的根评论，`replyToCommentId` 是实际被回复的评论。历史一级回复推导出原来的回复目标。已删顶层评论仍有回复时保留占位。已删的回复内容保持清空，已有后续回复仍在同一楼层可查。可选 `Idempotency-Key` 最长 128 字节，按博客和作者去重。重复请求返回同一个 `201` 和评论 ID，改变内容或回复目标时返回 `409`。

关系或评论与桶增量在同一事务提交。点赞和删评使用同一个用户所属桶，因此并发重试和取消沿用相同锁顺序。汇总 Worker 每秒尝试把增量加到旧展示列并清零待处理增量。更新展示列和清桶在一个事务里。历史点赞基数保留，区分个人最新操作与展示总数。指标 `hmdp_social_counter_projection_delay_seconds` 观察汇总延迟，详情缓存还可能保留上一个版本最多 3 秒。

## 详情、榜单、动态和通知

- 博客公共详情缓存 3 秒，Redis 租约合并跨进程回源。个人 `isLike` 每次独立查 MySQL。评论正文仍从 MySQL 读取。
- `GET /blog/hot?snapshot=true` 返回热门前 1,000 条的分页视图。快照每约 10 秒生成、保留 60 秒，游标固定榜单版本。过期返回 `410`，客户端刷新首页。原热门页码和游标继续可用。
- `SOCIAL_BOUNDED_FEED=true` 启用候选查询，每个关注作者通过索引提供最多 11 条。全局从中取最新项，批量查询显示信息。保留 `cursor`、`lastId` 和旧响应字段。
- 通知分片、租约、失败处理和缓存恢复见[社交通知的升级和运行](20-social-notification-fanout.md#升级和运行)。
- `SOCIAL_WRITE_CONCURRENCY` 每个 API 默认 12，社交写按本地并发预算拒绝过载。`MEDIA_UPLOAD_CONCURRENCY` 默认 2，单独限制图片读入、解码和上传。超载响应 `503` 和 `Retry-After`。

## 部署和回退

应用 `014` 和 `015`。当前版本的通知任务升级还需执行 `017`。执行期间暂停社交写入，旧展示列直接作为基数，待汇总表从空表开始。先完成所有进程升级再恢复写入。回退前暂停写入和通知生产，等待 `social_blog_counter_buckets` 中的脏标记与 `social_fanout_shards` 待处理记录归零，再切换模式或程序。已产生的多级回复保留平铺根 ID，旧代码可以读该楼层。修改选项时保持所有 API 一致。

## 本机复现

设置 `MYSQL_BIN_DIR`、`REDIS_BIN_DIR` 和 `KAFKA_BIN_DIR`。`social-hot` 默认造 100 万篇帖、爆帖 10 万条评论、其中一楼 1 万条回复，90% 的请求命中该帖。读、写、混合和 Feed 可通过 `SOCIAL_HOT_WORKLOAD=read|write|mixed|feed` 分开跑。`SOCIAL_HOT_RATE` 为每秒计划操作数，发评加删评计为一组操作。脚本记录调度丢弃、响应分布和 P99。

```bash
SOCIAL_COUNTER_BUCKETS=false SOCIAL_DETAIL_CACHE=false scripts/stage7-local.sh social-hot
SOCIAL_COUNTER_BUCKETS=true SOCIAL_DETAIL_CACHE=false scripts/stage7-local.sh social-hot
SOCIAL_COUNTER_BUCKETS=false SOCIAL_DETAIL_CACHE=true scripts/stage7-local.sh social-hot
SOCIAL_COUNTER_BUCKETS=true SOCIAL_DETAIL_CACHE=true scripts/stage7-local.sh social-hot
SOCIAL_HOT_WORKLOAD=matrix SOCIAL_HOT_SECONDS=5 SOCIAL_WRITE_CONCURRENCY=0 scripts/stage7-local.sh social-hot
SOCIAL_HOT_SECONDS=3600 SOCIAL_HOT_RATE=200 SOCIAL_HOT_ORDER_RATE=2 scripts/stage7-local.sh social-hot
```

## 3090 短压与故障验证

测试使用本机隔离的 MySQL 8.0.33、Redis 7.2.11 和 Kafka 4.1.2，以下容量矩阵的中间件数据位于 tmpfs，MySQL 配置提交刷盘，Redis AOF 为 `always`。同机器还有独立试验，矩阵对照采用相同的应用和数据参数。本机数值用于同负载对照。

写入组每轮 5 秒，以每秒 800 个操作安排提交，90% 集中于同一篇帖。第一轮单 API，后两轮双 API。发评加删评计一个操作。关闭社交写预算，测量数据库竞争和客户端调度丢弃。

| 模式 | 每轮成功操作 | 客户端调度丢弃 | 点赞 P99 | 发评加删评 P99 | MySQL 累计行锁等待 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 同行计数 | 3,002–3,157 | 843–998 | 173.9–237.5 ms | 284.4–393.9 ms | 92.586–189.090 秒 |
| 只开分桶 | 4,000 | 0 | 3.4–4.6 ms | 6.8–9.3 ms | 0.152–0.183 秒 |
| 只开缓存 | 3,052–3,180 | 820–948 | 200.8–211.2 ms | 296.0–329.2 ms | 93.240–188.457 秒 |
| 分桶与缓存 | 4,000 | 0 | 3.5–4.6 ms | 7.1–9.7 ms | 0.144–0.184 秒 |

每秒 800 个读操作时，各组每轮均成功 4,000 次。旧路径区间内 MySQL `Com_select` 增量为 5,160–5,164，分桶加缓存为 3,724–3,730，其中包含个人点赞和依赖监测等查询。详情 P99 从 2.224–2.360 ms 变为 2.458–2.811 ms，少了约 28% 的 SELECT，也增加了本机请求中的 Redis 检查开销。每秒 400 个混合操作时，各组每轮成功 2,000 次。矩阵各轮在汇总完成后计数对账通过。

热评查询的 `EXPLAIN ANALYZE` 在楼层中间以 `idx_comment_page` 从游标开始读取 21 条。被删楼层的可见性检查使用 `(blog_id, parent_id, deleted_at, id)` 索引。原执行计划可能选择主键范围和子查询全表扫描。新增回复计数和分页接口覆盖了跨帖拒绝、删除后的楼中楼、同键重试、个人点赞可见性和榜单版本游标。

每秒 120 次 Feed 读的独立对照中，旧查询出现超时和客户端丢弃。每作者候选方案也有高尾延迟，`EXPLAIN ANALYZE` 显示关注 2,000 人时，MySQL 仍会在每个作者下扫描约 500 条索引记录。默认改成按博客主键逆序查候选并探测关注关系，再只读取这一页详情。15 秒内完成 1,800 次操作、零丢弃；关注 10、500、2,000 人的 P99 分别为 23.384、12.636、3.796 ms。每作者候选保留为对照选项，默认关闭。主键逆序扫描在关注对象极少发帖时仍需监测扫描长度。

同机百万粉丝四帖场景分别对照原同步推送与两个持久化扇出 Worker。普通作者通知从 54.406 秒变为 1.012 秒，热门作者第三篇到尾部样本从 54.359 秒变为 55.858 秒。两组 Redis `ZADD` 同为 3,000,002，Kafka lag 与持久化任务最终均归零。任务拆批主要改善排队公平性。对配置为读时拉取的大 V，可以省掉对应 Redis 写入。

故障演练中，Worker 和 Kafka 停止期间发布文章，事件成功留在 MySQL Outbox。重启 Kafka 和 Worker 后注入 Redis 写暂停，期间可见批次超时并重试，随后任务完成、Outbox 清零，头尾通知样本可读。

追加验证中，两个作者各有 100 万关注关系，配置为读时拉取。两人各发三帖，普通作者发一帖。尾部读样本在各次发帖后的 57–72 ms 看到六条热门作者通知，普通作者样本为约 1.0 秒，Redis 仅写入两条普通推送。每秒 360 次混合 Feed 首页和深游标的追加对照中，默认查询完成 5,400 次，零丢弃，三种关注规模 P99 分别为 36.437、16.123、4.433 ms。

将历史展示点赞数设为 47 后，分桶新增点赞汇总为 48，取消后回到 47。对同一数据重复执行 `014` 和 `015` 无错误。上传预算的自动化测试挂起一个上传请求，验证下一次上传返回 `503`，同时普通路由仍可响应。

同一故障场景又在任务已领到租约、Redis 暂停写入时强制终止 Worker。重启后租约到期并重新处理，首、中、末三位粉丝的通知样本均可读。暂停 Redis 所有命令时，匿名详情通过受限的 MySQL 回源返回。升级验证在含历史记录的 `013` 库连续应用两次 `014` 和 `015`，旧评论、回复关系和历史计数均保留。

同样的百万粉丝推送额外在 `/disk2` 数据目录、Redis AOF `always` 下运行。约 18 分钟时，三项热门任务各完成约 68 万个关注者，普通作者任务已完成。该轮中止，完整对照使用 tmpfs，磁盘写入速度仍决定全量扇出的排空时间。

将写入计划速率依次提高到 800、1,600、2,400、3,200 和 4,800 操作/秒，每档 6 秒。单 API 和双 API 在 1,600 时各完成 9,600 个操作，零丢弃。1,600 档发评加删评 P99 分别为 38.3 ms 和 63.3 ms。2,400 档开始丢弃，单 API 和双 API 分别完成 12,119 和 11,834 个操作。该轮共用同规格 MySQL，客户端调度和服务端负载共同决定饱和点。复现用 `SOCIAL_HOT_WORKLOAD=sweep SOCIAL_HOT_SECONDS=6 SOCIAL_WRITE_CONCURRENCY=0`。

冷缓存测试让两台 API 同时请求一篇文章，32 个请求都在预设租约到期后成功返回。发帖后尽力撤销同 ID 的短缓存和租约，冒烟验证提前查过的不存在 ID 在发帖后立即可访问。

## 一小时混合压测

两台本机 API、一台 Worker，配置每秒 200 个社交操作和 2 笔真实秒杀。背景数据为 100 万帖和单帖 10 万评论。MySQL 和 Redis 数据位于 tmpfs。混压进程从最终评论索引和默认 Feed 查询合入前的版本构建。本节的长测反映该版本的尾延迟，最终评论索引另见短压。

| 路径 | 成功 / 调度数量 | P99 |
| --- | ---: | ---: |
| 博客详情 | 486,572 / 486,572 | 2.754 ms |
| 评论分页 | 161,668 / 161,669 | 946.609 ms |
| 发评加删评 | 35,897 / 35,897 | 8.493 ms |
| 点赞与取消 | 35,862 / 35,862 | 4.461 ms |
| 秒杀 HTTP 受理 | 7,200 / 7,200 | 2.23 ms |
| 秒杀接受请求到确认可查 | 3,600 / 3,600 个抽样 | 158.21 ms |

客户端没有调度丢弃。评论分页出现一次 `503`。汇总直方图共记录 8,866 次投影，均在 2 秒内，计数排空后核对零差异。秒杀库存、领取资格和订单记录均为 7,200 份一致，MySQL 和 Redis 剩余库存均为零。订单 Kafka 消费组 140 次样本的总 lag 均为零，结束时 Kafka 和 Redis 队列均排空。低社交流量的 180 秒对照中，360 笔秒杀全部确认，受理 P99 为 3.09 ms，确认可见 P99 为 161.48 ms。

最终构建以同样的社交与秒杀速率追加 120 秒。24,000 个社交操作全部成功，评论分页 P99 为 3.766 ms。240 笔订单全部确认，120 个确认抽样 P99 为 159.15 ms，库存和社交计数核对通过。最终版本的评论尾延迟目前有短压结果。
